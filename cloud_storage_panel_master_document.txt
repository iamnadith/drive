------------------------------------------------------------
1. PROJECT OVERVIEW
------------------------------------------------------------
The goal is to build a full cloud storage solution with:
- Hosted storage panel
- Multi-Cloudflare R2 account management
- Custom URL endpoints controlled by the panel
- User management, quotas, permissions
- File browser (Google Drive–style)
- Multi-bucket operations
- Full migration engine (20+ TB)
- Migration agents across multiple VPS nodes
- Auto-migration every 20 days
- Strong data integrity guarantees (practically 100%)
- Full documentation system embedded in the website
The system behaves as a “cloud storage provider” on top of Cloudflare R2, abstracting raw R2
complexity behind a modern, user-friendly panel and API.
------------------------------------------------------------
2. CORE COMPONENTS
------------------------------------------------------------
1) Web UI Panel
- Built with React / Next.js / Tailwind / shadcn UI.
- Provides full admin and user experience: buckets, files, links, migrations, accounts.
2) Backend API
- Node.js backend (NestJS or similar).
- Provides REST/JSON API for the UI and agents.
- Handles authentication, authorization, validation, scheduling, migrations, and verification.
3) Database (PostgreSQL)
- Stores user accounts, Cloudflare accounts, buckets, migration jobs, permissions, and audit logs.
4) Job Queue (Redis + BullMQ or equivalent)
- Manages long-running jobs (migrations, verifications, indexing, scheduled tasks).
5) Migration Agents
- Lightweight clients installed on VPS servers.
- Poll jobs from backend, perform high-throughput R2-to-R2 migrations using S3-compatible APIs.

6) Cloudflare R2 Integration
- Uses S3-compatible endpoints for file operations (list, upload, copy, delete).
- Uses Cloudflare REST APIs for R2 management (buckets, custom domains, public URLs).
7) File Browser & Endpoint Layer
- Implements a folder-like view on top of R2 object keys (prefix-based).
- Exposes panel-owned URLs for HTML previews and raw file access.
8) Search & Indexing
- Indexes objects metadata (name, size, type, path, owner) to support powerful search and filters.
9) Documentation System
- Built-in documentation pages explaining how to use the panel, endpoints, and features.

4. SYSTEM ARCHITECTURE
------------------------------------------------------------

Core flows:
1. UI -> Backend
- The frontend calls backend REST endpoints for all actions (login, list files, create migration,
etc.).
2. Backend -> R2
- For file operations: uses S3-compatible R2 endpoints with per-account credentials.
- For bucket and configuration operations: uses Cloudflare REST APIs.
3. Backend -> Agents
- Agents communicate via backend endpoints (polling or lightweight WebSocket if desired).
- Backend assigns jobs, receives progress, and updates migration status.
4. Backend -> Database & Queue
- All state is persisted in PostgreSQL.
- Long jobs scheduled via a queue system (Redis + BullMQ).
5. Auto-Migration
- A scheduler process periodically checks for accounts where last migration is older than the
configured interval (e.g. 20 days).
- Creates or queues appropriate migration jobs.

6. CLOUDFLARE ACCOUNT MANAGEMENT
------------------------------------------------------------
Features:
- Add Cloudflare accounts by providing:
  - account_id
  - R2 access key & secret
  - Optional Cloudflare API token
- Accounts are persisted in cf_accounts with sensitive fields encrypted.
- Each account has:
  - status: "active" or "disabled"
  - auto_migrate_enabled: boolean
  - migrate_interval_days: integer (default 20)
  - migrate_to_account_id: account where data will be migrated to
  - last_migrated_at: datetime
  - UI option to manually mark as active/disabled
  - UI option to run migration now
Rules:
- Only "active" accounts are used for new writes / operations.
- After a full successful migration from account A to account B, account A is typically set to
"disabled".
- Admins can override and re-enable accounts when needed.

8. FILE LINKS & ENDPOINTS
------------------------------------------------------------
The panel provides user-facing links based on its own domain.
Endpoint types:
1) HTML file view
- URL: /f/:accountSlug/:bucket/*objectPath
- Behavior:
  - Checks user or link token permissions.
  - Renders viewer page with metadata and preview.
  - Uses backend to fetch metadata and either proxy or redirect to R2 URL.
2) Raw file download/stream

- URL: /raw/:accountSlug/:bucket/*objectPath
- Behavior:
  - Authorization check.
  - Option 1: directly proxy data from R2 via backend stream.
  - Option 2: generate a short-lived signed R2 URL and redirect.
3) Public share link
- URL: /p/:shareToken
- Behavior:
  - shareToken maps to file + share config (optional password, expiry, download limits).
  - If token valid and active:
    - Either show HTML view or redirect to /raw URL according to share mode.
Access Modes:
- Private: only authenticated users with access can view.
- Public link: unguessable share link; good for public file sharing.
- Time-limited signed URLs: valid until expiration; used for private access without login.

9. USER MANAGEMENT, STORAGE LIMITS & PERMISSIONS
------------------------------------------------------------
User Roles:
- Admin
  - Full access to all accounts, buckets, users, migrations, agents, settings.
- Manager
  - Can manage users within limits, see most buckets, start migrations, etc. (configurable).
- User
  - Restricted to their assigned buckets/spaces.
- Viewer
  - Read-only access per assigned buckets/spaces.
Storage Limits:
- Each user has storage_limit_bytes (nullable for unlimited).
- Each user owns one or more spaces (logical views into R2).
- Each upload increments the space used_bytes; delete decrements.
- System enforces quota before each upload.
Bucket Permissions:
- bucket_permissions assigned per user:
  - access_level values:
    - "read": list and read files
    - "write": upload, rename, delete own files
    - "admin": can manage bucket configuration (for that bucket)
Admins bypass bucket_permissions and see all accounts/buckets by default.

10. MIGRATION ENGINE (DIRECT + CLOUDFLARE)
------------------------------------------------------------
Migration Modes:
Mode: "direct"
- Uses custom migration agents running on VPS servers.
- Agents pull jobs from backend and perform S3-based copy operations.
- Suitable for R2-to-R2 cross-account migrations and very large data sets.
Mode: "cloudflare"
- Uses Cloudflare migration tools (e.g., Super Slurper) when possible.
- Backend helps configure and track such migrations.
- After migration, backend verifies data by scanning destination via API.
Migration Job Lifecycle:
- Created with:
  - source_account_id, dest_account_id
  - optional bucket/prefix filters
  - mode ("direct" or "cloudflare")
  - options (concurrency, bandwidth limits, verification options)
- Status transitions:
  - pending -> running -> verifying -> completed or failed
- Verification phase:
  - Compares object lists between source and destination.
  - Checks sizes and optionally ETags/hash.
  - Logs differences and attempts repair when configured.

11. MIGRATION AGENT ARCHITECTURE
------------------------------------------------------------
Agent Installation:
- User runs a script on a VPS:
  - Example:
    curl -s https://panel.example.com/install-agent.sh | bash -s -- --server
https://panel.example.com --token AGENT_TOKEN
- Script:
  - Downloads agent binary or Docker image.
  - Writes config with server URL and agent token.
  - Installs as a systemd service.
Agent Behavior:
- On startup:
  - Registers with backend using the token.

  - Receives a unique agent id.
- Main loop:
  - Sends heartbeat regularly.
  - Polls /next-job endpoint for assigned work.
  - Executes migration jobs with multi-threaded R2 copy logic.
  - Reports progress and events.
  - On completion:
    - Reports success or failure.
Multi-Agent Support:
- Multiple agents can run in parallel across different VPS servers.
- Large migrations are split into sub-jobs (e.g., by key prefix).
- Backend assigns sub-jobs to available agents, balancing load.

12. RECURRING 20-DAY AUTO-MIGRATION
------------------------------------------------------------
Auto-Migration Logic:
- A scheduled process runs periodically (e.g., every hour).
- For each account in cf_accounts:
  - If auto_migrate_enabled = true AND status = "active"
  - AND (last_migrated_at is NULL OR now - last_migrated_at >= migrate_interval_days)
  - THEN:
    - Create a migration_job from this account to migrate_to_account_id.
    - Set last_migrated_at to the job start time or completion time based on design.
Post-Migration Actions:
- When verification passes:
  - Set source account status = "disabled"
  - Set destination account status = "active"
  - For all buckets and spaces referencing the old account:
    - Update them to point to the new account or equivalent destination buckets.
  - Log an audit entry recording the account switch.
Manual Controls:
- Admin can:
  - Disable or enable auto-migration per account.
  - Change migration interval.
  - Change migration target account.
  - Manually trigger migration outside of schedule.

13. DATA INTEGRITY & ACCURACY STRATEGY
------------------------------------------------------------
Objective:

Achieve practical 100% accuracy for migrations and operations, with transparency of any deviations.
Key Techniques:
1) Double-Phase Migration (Copy + Verify)
- Phase 1: Copy all objects from source to destination.
- Phase 2: Verify:
  - Object count equality.
  - Total bytes equality.
  - Optional per-object match (size and ETag) for all or sampled objects.
2) Repair Sub-Jobs
- If mismatches detected:
  - Create repair jobs to recopy missing or mismatched objects.
  - Re-run verification on affected subset.
3) Idempotent Design
- Migration jobs and sub-jobs can be safely re-run.
- Copy operation only overwrites when objects differ or when forced.
4) Checkpoints
- For large sets, store last processed key/prefix to resume on crash or restart.
5) Reporting
- Migration job exposes detailed results in the UI.
- Admins can view mismatch lists and repair logs.
The system does not mark the migration as "final" until verification passes or the admin explicitly
accepts known, documented discrepancies.

17. FAILURE SCENARIOS & RECOVERY
------------------------------------------------------------
Potential Failures:
1) Network interruptions during migration
- Recovery: resume from last checkpoint and retry chunks/objects.
2) Agent crash or VPS outage
- Recovery: job remains in "running" but with heartbeat timeout; backend reassigns remaining work to
another agent.
3) Cloudflare API errors or throttling
- Recovery: exponential backoff and retry logic; log warnings.
4) Data mismatches on verification
- Recovery: repair sub-jobs recopy problematic objects; admin view shows details.
5) Database outage
- Recovery: run migrations with transaction safety; restart worker when DB is back; do not lose
state of jobs already persisted.
